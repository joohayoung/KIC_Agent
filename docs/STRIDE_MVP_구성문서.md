# 1. 개요 및 MVP 전략 방향

본 문서는 한국투자공사(KIC)의 투자 기업 발굴 및 사전 심사 지원을 위해 구축되는 STRIDE(Sovereign Tech & Resource Investment Discovery Engine) 시스템의 MVP 구성과 노드 설계를 정의한다.

KIC는 정부와 한국은행으로부터 위탁받은 외환보유액을 운용하는 국부펀드로서 상업적 수익성과 국가 경제안보·전략산업 지원이라는 공적 책무를 함께 수행한다. 2027년 출범 예정인 국내 전략투자계정 신설과 국내 기업 해외진출 공동투자 플랫폼 활성화가 주요 현안이다.

## 1.1 MVP 개발 대상

전체 8개 분석 요소(STRIDE 멀티에이전트 구성 문서 기준) 중 본선 기간 내 확실히 동작하는 시스템을 위해 2개 전문 영역과 이를 묶는 오케스트레이터, 검증 에이전트만 개발한다.

- **해외진출 자금수요 (overseas_funding)**: 해외 공장 증설, 현지 지분인수 등 해외 성장투자 신호를 공시·뉴스에서 추출하고, 진행 단계와 자금 공백(Funding Gap)을 계산한다.
- **재무 건전성 (financial_health)**: 재무제표와 KRX 시장 데이터로 재무·시장 지표를 계산하고, 출처 방법론의 구간에 매핑한다. 결격 여부는 판단하지 않는다.
- **검증 (verifier)**: 새 데이터를 모으지 않고 근거 원문, 기준일, 에이전트 간 수치 일치, 최종 답변 문장을 대조한다.
- **오케스트레이터 (orchestrator)**: 탐색 조건 해석, 후보 기업 탐색, 실행 계획, 결격·주의 규칙 적용, 발굴 보드와 사전검토서 작성. **판단은 여기서만 한다.**

## 1.1A 사용 시나리오: 조건만 넣으면 기업을 찾아준다

KIC 심사역은 대상 기업을 모르는 상태에서 시작한다. 입력하는 것은 기업명이 아니라 **탐색 조건**이다.

> 예: "최근 1년 안에 미국·유럽에 공장 신설이나 증설을 공시한 코스피·코스닥 제조업체 중, 해외 투자액이 보유 가용자금보다 큰 기업"

1. 오케스트레이터가 조건을 구조화하고 해석 결과를 사용자에게 확인받는다.
2. 상장사 전체에서 조건에 맞는 공시가 있는 기업을 결정론으로 좁힌다.
3. 남은 후보만 두 전문 에이전트로 심층 분석한다.
4. 결격 규칙과 사용자 조건을 적용해 **발굴 보드**를 만든다.
5. 심사역은 보드에서 기업을 골라 사전검토서를 보고, 관심 기업이나 탐색 조건을 저장한다.
6. 추적형이 새 공시마다 저장된 조건과 관심 기업을 대조해 새로 맞는 기업과 변경 사항을 알린다.

기업명을 직접 넣는 기업 지정 검토(`review_graph`)는 보조 기능으로 남긴다. 이미 알려진 기업을 확인하거나 보드에서 기업을 선택했을 때 이 흐름이 실행된다.

v1.4 화면 흐름(8장):
- 처음 들어오면 **관심 기업 추적** 페이지: 추적 중인 조건별 새로 맞은 기업·빠진 기업, 관심 기업 최신 상태와 변경 내역.
- **기업 발굴** 페이지: 탭(조건 세트)을 고르거나 새 조건을 자연어로 입력 → 조건 칩 확인 → 후보 기업 표. 저장한 조건이 없어도 'STRIDE 기본 탐색' 탭이 있다.
- **기업 상세** 페이지: 사전검토서.
- 상단 질의창은 세 페이지 공통이다. "가나정밀 검토해줘", "○○ 자금 공백이 왜 늘었어?", "자금 공백 30% 이상만" 같은 입력을 의도별로 처리한다.

## 1.2 최우선 원칙: 개별 에이전트는 판단하지 않는다

| 구분 | 개별 에이전트 (ovs, fin, verifier) | 오케스트레이터 |
|---|---|---|
| 하는 일 | 수치 계산, 근거 수집, 규칙 기반 분류, 출처 구간 매핑, 불일치 보고 | 결격·주의 규칙 적용, 종합 의견, 실사 확인 목록 작성 |
| 금지 | score, rank, rating, grade, recommendation, priority 필드. '유망', '양호', '위험', '추천' 같은 평가어 | 출처 없는 기준으로 판정 |
| 출력 | `AgentResult` (metrics, classifications, findings, alerts, evidence, report_markdown) | `FinalReport` |

v1.5부터 개별 에이전트는 구간 매핑도 하지 않는다. 값·기간·산식 출처만 낸다. 그 값이 투자에 적합한지는 출처 있는 규칙으로만 오케스트레이터가 말한다.

# 2. 2개 실행 스택 구조 (요청형 vs 추적형)

새 에이전트를 만들지 않고, 같은 오케스트레이터에 진입 그래프 3개를 둔다. 요청형 스택에 `discover_graph`(조건 탐색, 기본)와 `review_graph`(기업 지정 검토, 보조), 추적형 스택에 `monitor_graph`가 있다. 세 그래프는 같은 전문 에이전트와 같은 SQLite 상태를 공유한다.

![\[그림 1\] STRIDE 2개 실행 스택과 사용자 화면](STRIDE_MVP_figs_v1.5/d1.png){width="6.5in"}

| 구분 | 스택 1-A: 조건 탐색 (discover) | 스택 1-B: 기업 지정 검토 (review) | 스택 2: 추적형 (monitor) |
|---|---|---|---|
| 트리거 | 화면의 탐색 조건 입력 | 보드에서 기업 선택, 또는 기업명 직접 입력 | Windows 작업 스케줄러, 1일 2회. 실행 시각은 DART 공시 접수 시각 분포를 확인한 뒤 확정 |
| 입력 | 자연어 조건 또는 조건 폼 → `DiscoveryCriteria` + 기준일(as_of) | 기업명/종목코드 + as_of | 직전 실행 커서, 저장된 탐색 조건, 관심 기업 목록 |
| 실행 흐름 | 조건 해석·확인 → 후보군 구성 → 공시 스캔 → 1차 필터 → ovs ‖ fin 배치 → 검증 → 결격 규칙 → 조건 적용 → 보드 | 기업 확정 → ovs ‖ fin 병렬 → 검증 → 결격 규칙 → 검토서 → 답변 검증 | 커서 이후 공시 조회 → 중복 제거 → 공시유형별 에이전트 호출 → 검증 → 저장 조건 대조 → 직전 상태와 비교 → 알림 |
| 산출물 | 발굴 보드 + 탐색 단계별 기업 수 | KIC 투자심의 사전검토서 | 관심 기업 추적 화면 항목(신규 매칭·조건 이탈·변경, `orc_feed`), 보드 갱신, 주간 다이제스트 |
| 비용 통제 | 결정론 필터로 후보를 줄인 뒤 상위 K개만 심층 분석 | 단일 기업이므로 두 에이전트 항상 실행 | 공시유형 규칙표로 필요한 에이전트만 호출 |

PC가 꺼져 실행을 놓쳐도 다음 실행 때 커서 이후 공시를 모두 처리하므로 누락되지 않는다.

**공통 진입: `route_intent` (v1.4)** — 상단 질의창 입력은 먼저 의도를 분류한다(LLM 1회). 상세는 오케스트레이터 개발문서 7.1·7.4·7.5.

| 의도 | 예시 | 처리 |
|---|---|---|
| 새 탐색 | "동남아에 공장 짓는 소재 기업 찾아줘" | discover_graph (조건 해석·확인부터) |
| 기업 검토 | "가나정밀 검토해줘" | review_graph |
| 결과 질문 | "한빛소재 자금 공백이 왜 늘었어?" | `answer_graph`: 저장된 결과·근거만으로 답변, 새로 수집하지 않음 |
| 보드 필터 | "자금 공백 30% 이상만" | `board_filter`: 지금 표에 표시 필터. 지역·업종·기간 변경은 다시 탐색 안내 |
| 알 수 없음 | — | 되묻기 |

화면과 실행 프로세스는 `orc_jobs` 테이블로 주고받는다(화면_데이터_연결명세 1.3). 화면은 DB를 읽기만 한다.

# 3. MVP 에이전트 구성 및 역할

오케스트레이터 1개와 전문 에이전트 3개로 구성한다. 에이전트 간 데이터는 Pydantic 스키마(`AgentResult`, `VerificationReport`, `FinalReport`)로만 주고받는다.

![\[그림 2\] MVP 에이전트 구조와 데이터 흐름](STRIDE_MVP_figs_v1.5/d2.png){width="6.5in"}

| 에이전트 | 식별 키 | 역할 | 대표 출력 (metrics_catalog.yaml ID) |
|---|---|---|---|
| 오케스트레이터 | orchestrator | 조건 해석, 후보 탐색, 계획, 결격 규칙 적용, 보드·검토서 합성 | DiscoveryBoard, FinalReport, rule_results |
| 해외진출 자금수요 | overseas_funding | 해외투자 신호(S1·S2·S4·S5·S6) 추출, 단계 분류, 자금 공백 계산 | ovs.funding_gap, ovs.funding_gap_ratio, ovs.overseas_investment_amount, ovs.project_stage, ovs.signal_status, ovs.in_scope |
| 재무 건전성 | financial_health | 재무·시장 지표 계산, 출처 구간 매핑, 감사의견·자본잠식률 수집 | fin.net_debt_to_ebitda, fin.ebitda_interest_coverage, fin.ebitda_margin, fin.capital_impairment_ratio, fin.audit_opinion 외 (4.4 참조) |
| 검증 | verifier | 근거·기준일·교차 일치·커버리지 대조, 최종 답변 대조 | VerificationReport (불일치·미확인 목록) |

**지표 소유권**: 가용자금 구성 항목(fin.cash_and_equivalents, fin.short_term_financial_assets, fin.ttm_operating_cash_flow)은 재무 에이전트가 정의를 소유하고 `core.calc` 공용 함수로 구현한다. 해외진출 에이전트는 이 함수를 호출해 자금 공백을 계산한다. 두 에이전트가 같은 값을 다르게 계산하지 않게 하기 위함이다.

**카탈로그 등록**: 4.4의 `fin.*` 지표는 metrics_catalog.yaml v0.2에 `status: draft`로 등록했다. 산식 세부(EBITDA 구성, 계정 ID)는 재무 에이전트 개발문서에서 확정하고, 실제 데이터로 검증하면 `confirmed`로 바꾼다.

# 4. 노드 설계 및 조건부 분기

모든 그래프는 LangGraph StateGraph로 만든다. 계산은 Python 함수, 텍스트 해석은 LLM으로 노드를 분리한다.

## 4.0 오케스트레이터: discover_graph (조건 탐색, 요청형 기본)

**입력 스키마 `DiscoveryCriteria`**

| 필드 | 예시 | 비고 |
|---|---|---|
| markets | KOSPI, KOSDAQ | 시장 구분 |
| industries | 제조업(표준산업분류 C) 하위 업종 | OpenDART 기업개황(company.json)의 `induty_code` 기준 |
| target_regions | 미국, EU, 동남아 | 투자 대상 국가·지역 |
| investment_types | 신설, 증설, 지분 인수(M&A) | ovs 분류값과 동일 |
| stages | Stage 1~5 중 선택 | ovs.project_stage |
| min_investment_amount | 500억 원 이상 | ovs.overseas_investment_amount |
| min_funding_gap_ratio | 선택 (기본 없음) | ovs.funding_gap_ratio. 값이 없으면 제외하지 않고 확인 필요 |
| market_cap_range | 선택 | fin 시장 지표. 시장 데이터가 없으면 이 조건은 '확인 불가'로 표시 |
| exclude_rules | 5장 규칙 해당 기업 제외 여부 | 기본값은 제외하지 않고 표시만 |
| lookback | 최근 12개월 | 공시 스캔 기간 |
| as_of | 기준일 | 없으면 오늘 |
| max_deep_analysis (K) | 20 | 심층 분석할 최대 기업 수. 첫 실제 실행은 5곳 (`first_run_max_deep_analysis`) |

조건은 **사용자가 정한 기준**이다. 시스템은 조건에 맞는지 사실만 대조하고, 조건 자체를 만들거나 바꾸지 않는다.

**탐색 = 조건 한 세트 (v1.4)**: 화면의 탭 1개가 `orc_searches` 1행이다. 탭 안의 조건은 모두 동시에 만족해야 한다(AND). 같은 기업·같은 as_of 분석 결과는 탐색끼리 공유하므로 탐색 수가 늘어도 분석 비용이 늘지 않는다. 저장 구조는 오케스트레이터 개발문서 9장(`orc_searches`, `orc_search_runs`, `orc_search_matches`, `orc_watchlist`).

**STRIDE 기본 탐색 (v1.4)**: 시스템이 시드하는 탐색 1개(`is_system=1`, 삭제 불가, 복제 가능).

| 조건 | 정의 | 근거 |
|---|---|---|
| 해외투자 계획 확인 | scope_gate G1~G4 통과 (진행 단계 1~5) | 해외진출 에이전트 scope_gate 7.9 |
| 확정 신호 | 대표 프로젝트에 S4(취득·투자 결정) 또는 S5(해외 용도 조달) | 해외진출 에이전트 7장 |

(2026-11-10 방향 수정) 자금 공백 > 0과 상장 규정 기준 제외는 기본 조건에서 뺐다. 값이 없는(missing) 지표는 어떤 조건에서도 기업을 제외하지 않는다. 표에는 다음 4축을 점수·등급·가중합 없이 나란히 보여준다.

| 축 | 지표 | 출처 |
|---|---|---|
| A 해외 진출 신호 | S4, S5, S6 주 신호, S1·S2 보조 신호와 출처 등급 | 해외진출 에이전트 |
| B 유동성 원천·소요 | 원천 ÷ 소요, 원천 − 소요, 항목별 값 (1배 선만, 구간 없음) | S&P Liquidity Descriptors(2014, 2019 가이드) 준용 STRIDE 정의. 원문 403으로 문단 미확인. 해외진출 개발문서 11.2a |
| C 차입 여력 | 부채비율, 순차입금/EBITDA, EBITDA/이자비용 | 한국기업평가 「주요 재무지표의 정의」 |
| D 재무 위험 | 자본잠식률, 자기자본, 감사의견, 회생·워크아웃 공시, 거래 상태 경고 | 한국거래소 공시가이드(2026.2.2), 5장 |

"재무가 좋다"는 조건은 두지 않는다. 재무 지표는 값과 출처로만 보여준다. 화면 하단 고정 문구: "공시로 확인되는 항목만 반영(은행 약정 한도·회사 전망치 미포함)".

**노드**

| 노드 | 종류 | 내용 |
|---|---|---|
| parse_criteria | LLM | 자연어 조건 또는 폼 입력 → `DiscoveryCriteria`. 해석할 수 없는 표현은 `unparsed` 목록으로 남김 |
| confirm_criteria | 중단·재개 | 해석 결과를 조건 칩으로 화면에 보여주고 사용자 확인을 받음(LangGraph `interrupt`). 수정하면 다시 해석 |
| build_universe | 결정론 | 상장사 corp_code 목록에서 시장·업종 조건으로 후보군 구성. 기업개황은 SQLite에 캐시 |
| scan_events | 결정론 | `lookback` 기간의 공시 목록(list.json)을 공시유형으로 조회해 해외투자 관련 공시(4.2 규칙표의 유형)가 있는 기업만 남김. 이미 분석한 결과가 상태 DB에 있고 이후 신규 공시가 없으면 재사용 |
| prefilter | 결정론 | 주요사항보고서 구조화 필드(DS005)로 바로 확인되는 조건(투자 대상 국가, 투자액)을 적용. 남은 기업이 K개를 넘으면 최근 공시일 순으로 K개를 심층 분석하고, 나머지는 '심층 분석 대기'로 보드에 표시 |
| dispatch (batch) | 결정론 | 기업별로 ovs ‖ fin 실행. 기업 단위로 진행 상황을 `runs` 테이블에 기록(화면 진행 표시용) |
| verifier(results) | 결정론 + 원문 재조회 | 4.5 참조 |
| check_sufficiency | 결정론 | 필요 지표(`REQUIRED_METRICS`)의 data_status 확인. 부족한 기업만 `replan` (v1.4) |
| replan | LLM (D1) | 기업당 최대 1회, 허용 행동 중 선택 (4.6) (v1.4) |
| apply_rules | 결정론 | 5장 규칙 적용 |
| apply_criteria | 결정론 | 심층 분석 결과로 나머지 조건 대조. 충족하지 않으면 제외 사유(어떤 조건, 어떤 값)와 함께 '제외 목록'에 보관 |
| plan_followup | LLM (D4) | 결과가 0건이거나 확인 불가가 많을 때 조건 완화·기간 확장을 **제안만** 함. 실행은 사용자가 확인한 뒤 |

## 4.3 해외진출 자금수요 에이전트 (overseas_funding)

상세는 「해외진출 자금수요 기업 발굴 에이전트 개발문서 v0.4」가 기준이다. 아래는 13개 노드를 단계별로 묶은 요약이며, 노드 이름은 개발문서를 따른다.

| 단계 | 개발문서 노드 | 내용 |
|---|---|---|
| 1. 입력 | parse_request, resolve_company | 요청 검증, 기업 확정 |
| 2. 수집 | collect_disclosures, collect_news | as_of 이전 공시(접수일 기준)·뉴스(보도일 기준)만 수집 |
| 3. 추출 | extract_periodic_plan, parse_major_events, extract_news | 정기보고서 계획 문단(LLM), 주요사항보고서 구조화 필드(결정론), 뉴스 신호(LLM). 정기보고서는 전문을 넣지 않고, 개발문서 8.4의 `dart_sections.py`로 필요한 섹션(사업의 내용, 시설투자 등)만 잘라 LLM에 넣는다 |
| 4. 통합·분류 | merge_signals, scope_gate | 출처 간 신호 병합과 충돌 기록, 범위 규칙 G1~G5 적용 |
| 5. 계산 | compute_funding_gap | 자금 공백 = 해외투자액 − (현금 + 단기금융자산 + TTM 영업현금흐름(음수 그대로) + 확정 해외 조달액). 가용자금은 `core.calc` 호출 |
| 6. 검증 | verify | 추출 주장 재대조. 실패 시 재추출 (최대 2회) |
| 7. 저장·보고 | update_state, write_report | 상태·이력 저장, 사실 요약 작성(평가어 금지) |

부정 신호(S6: 연기·철회·정정)와 보도·공시 간 금액 차이는 이 에이전트가 `merge_signals`에서 기록한다. 검증 에이전트가 다시 수집하지 않는다.

v1.3에서 이 에이전트에 LLM 판단 지점 D2(`collect_news` 검색어 생성)와 D3(`merge_signals` 이후 원문 추가 확인)를 추가한다(4.6). 개발문서 v0.4의 해당 노드 명세는 v0.5에서 갱신한다.

**지표 구성** (재무 건전성 개발문서 v0.2 3장. 모든 지표 사업연도별, 구간 표시 없음)

| 구분 | 지표 | 산식 | 출처 |
|---|---|---|---|
| 핵심 | 순차입금/EBITDA | (총차입금 − 현금성자산) / EBITDA | 한국기업평가 「주요 재무지표의 정의」 (EBIT 자리에 영업이익) |
| 핵심 | EBITDA/이자비용 | EBITDA / 이자비용 | STRIDE 정의 (한기평 EBITDA/금융비용과 분모 다름, note 표시) |
| 핵심 | EBITDA 마진 | EBITDA / 매출액 × 100 | 한국기업평가 정의 |
| 상장 규정 입력 | 자본잠식률, 자기자본(비지배지분 제외), 감사의견·감사범위 제한 | KIND 산식 | 한국거래소 KIND 유가증권·코스닥 공시가이드 (2026.2.2) |
| 보조 | 부채비율, 차입금의존도 / 유동비율 | 한기평 정의 / 표준 산식 | 한국기업평가 정의 / STRIDE 정의 |
| 참고 (선택) | 순차입금/EV, PER, PBR, EV/EBITDA | 시가총액 기반 | STRIDE 정의 (시장 데이터 키가 있을 때만) |
| 사실 표시 | 회생·워크아웃·파산 관련 공시 | 공시명 패턴 | DART 공시 (규칙 아님) |

**시가총액 대체 경로 유의사항**

- 「금융위원회_주식시세정보」는 기준일 다음 영업일 오후 1시 이후 갱신된다. as_of가 오늘이면 직전 거래일 값을 쓰고, 그 날짜를 evidence_id에 남긴다.
- 응답 필드(종가, 상장주식수, 시가총액 등)는 개발 시 활용자 가이드로 확인한다. 시가총액 필드가 없으면 같은 날짜의 종가 × 상장주식수로 계산한다. 사업보고서의 발행주식수는 시점이 기준일과 달라 쓰지 않는다.
- 이용허락은 공공누리 제4유형(출처표시, 상업적 이용 금지, 변경 금지)이다. PoC에는 문제없지만 서비스 단계에서는 다시 확인한다.
- 증권사 웹페이지 크롤링은 이용약관과 화면 구조 변경 문제로 쓰지 않는다.

**MVP 제외 항목**: 차입금 만기 구조와 계속기업 불확실성 문단은 감사보고서·주석 원문 파싱이 필요하다. MVP에서는 수집하지 않고 검토서에 '실사 확인 필요(needs_due_diligence)'로 표시한다.

## 4.5 검증 에이전트 (verifier)

새 데이터를 수집하지 않는다. 근거 원문 재조회만 허용한다.

| 모드 | 점검 항목 | 실패 시 |
|---|---|---|
| results | ① 모든 수치에 evidence_id 존재 ② 근거 원문의 값과 일치 ③ 근거 날짜 ≤ as_of ④ 같은 지표 ID를 두 에이전트가 냈을 때 값 일치 ⑤ 필수 지표 커버리지 ⑥ 금지 필드·평가어 없음 | 불일치·미확인 목록을 `VerificationReport`로 오케스트레이터에 반환 |
| answer | ① 검토서의 숫자가 AgentResult 값과 일치 ② 각주 evidence_id 실존 ③ 문장의 사실 주장이 근거와 일치 ④ 출처 없는 판단 표현 없음 | 오케스트레이터가 1회 재작성 |

검증 에이전트는 등급을 매기지 않는다. 실사 확인 목록은 오케스트레이터가 이 불일치·미확인 목록과 `needs_due_diligence` 지표를 모아 만든다.

## 4.6 LLM 판단 지점 (제한된 자율성)

그래프의 뼈대(노드 순서)는 고정한다. LLM이 다음 노드를 자유롭게 고르게 하면 실행마다 경로가 달라져 재현성·검증·판단 분리가 깨지기 때문이다. 대신 **정해진 위치에서만** LLM이 **허용된 선택지 중 하나**를 고른다.

| ID | 위치 | LLM이 고르는 것 | 허용 선택지 | 제한 |
|---|---|---|---|---|
| D1 | orchestrator `fill_missing` (review·discover 공통, 2026-11-11) | 빈 지표 값이 적힌 곳을 찾기 위해 다음에 볼 자료 | 읽기 전용 조사 도구 6개(기사 검색 제외) 중 하나 또는 종료 | 기업당 루프 1회, 최대 6스텝·LLM 6회. 찾은 값은 채택 게이트(코드 재확인) 통과 시만 채택 |
| D5 | orchestrator 감시 `investigate` (2026-11-11) | 새 공시의 의미 확인을 위해 다음에 볼 자료, 알림 시점, 조사 요약 | 조사 도구 7개 중 하나 또는 종료(immediate/digest + 문장) | 공시 1건당 루프 1회, 감시 1회 상한 = 재분석 상한. 요약은 검증 에이전트 통과분만 |
| D2 | ovs `collect_news` | 뉴스 검색어 | 공시에서 추출한 기업명·국가·프로젝트명·현지법인명의 조합만 허용 | 검색어 최대 3개. 공시에 없는 고유명사는 검증에서 거부 |

| D4 | discover `plan_followup` | 결과가 0건이거나 확인 불가가 많을 때 다음 제안 | `suggest_relax(field)`(특정 조건 완화 제안), `suggest_extend_lookback`(기간 확장 제안), `none` | **제안만 함**. 실행은 사용자 확인 후 |

**에이전트 자율성 범위 (2026-11-11)**: 자율은 '무엇을 더 찾아볼지'에만 준다.

| 구분 | 누가 정하나 | 내용 |
|---|---|---|
| 조사 경로 선택 | **에이전트(자율)** | 빈 값·새 공시에 대해 어느 공시·절·주석·첨부·기사를 더 볼지, 언제 그만 볼지 (조사 루프, 최대 6스텝·LLM 6회) |
| 알림 시점 | **에이전트(자율)** | 새 공시 조사 결과의 알림 시점: 즉시(immediate) / 다음 요약(digest) |
| 조사 요약 문장 | **에이전트(자율)** + 검증 | 1~3문장. 검증 에이전트(answer 모드)를 통과한 문장만 남긴다 |
| 숫자 채택 | **규칙(코드)** | 채택 게이트: 같은 접수번호 원문에서 같은 표·행을 다시 읽어, 기대 보고서(기간)·원화 단위·연결/별도·당기 열·허용 행 이름·값이 모두 맞을 때만. 채택 값은 코드가 읽은 값 |
| 어떤 행이 그 지표인가 | **규칙(코드)** | 지표별 허용 행 이름 목록(`orchestrator/fill.py` ALLOWED_ROWS). 목록 밖 행은 기각 |
| 파생 지표 재계산 | **규칙(코드)** | 기존 계산 함수(`calc/funding.py`, `core/calc/ratios.py`)와 CALC 근거 재계산 검사 |
| 상태 변경 | **규칙(코드)** | 프로젝트 연결(S6 정형 연결), 단계, 경보 종류 — 해외진출 7.12 그대로 |
| 시점 통제 | **규칙(코드)** | 모든 도구가 as_of를 받고 접수일·보도일이 as_of 뒤인 것은 돌려주지 않는다 |

**구현 방식**

- 판단 노드는 LangGraph 조건부 엣지의 라우터 함수로 만들고, LLM 출력은 Pydantic 모델 `RouteDecision(action: Literal[...], reason: str, evidence_ids: list[str])`로 받는다.
- 결정론 검증기가 선택지 범위, 반복 한도, 근거 존재를 확인한다. 검증에 실패하면 기본 경로(D1은 `mark_missing`, D3는 `record_conflict`)로 간다.
- 모든 결정은 `decisions` 테이블(run_id, 위치, 선택, 이유, 근거, 소요 시간)에 저장하고, `python -m stride.cli show --run-id`로 확인한다(8.1).
- 계산, 결격 규칙, 조건 대조는 LLM 판단 지점에 포함하지 않는다.

# 5. 결격·주의 규칙 (오케스트레이터 apply_rules)

규칙은 **원문으로 확인한 것만** 둔다. 결과는 '탈락'이 아니라 "어떤 공식 기준에 해당하는가"라는 사실로 표시하고, 실행을 중단하지 않는다. 기업의 시장 구분에 맞는 규칙만 적용한다. 출처: 한국거래소 KIND 유가증권시장·코스닥시장 공시가이드(2026.2.2, 2026-11-04 원문 확인).

| 규칙 ID | 시장 | 조건 | 결과 표시 |
|---|---|---|---|
| R1-KS | 유가증권 | 최근 사업연도 감사의견 부적정 또는 의견거절 | 상장폐지 사유 해당 |
| R1b-KS | 유가증권 | 감사범위 제한에 따른 한정 | 관리종목 지정 사유 해당 |
| R2-KS | 유가증권 | 최근 사업연도말 자본전액잠식 | 상장폐지 사유 해당 |
| R3-KS | 유가증권 | 자본잠식률 50% 이상 | 관리종목 지정 사유 해당 |
| R1-KQ | 코스닥 | 부적정, 의견거절, 또는 감사범위 제한에 따른 한정 | 상장폐지 사유 해당 |
| R2-KQ | 코스닥 | 자본전액잠식 | 상장폐지 사유 해당 |
| R3-KQ | 코스닥 | 자본잠식률 50% 이상 또는 자기자본 10억 원 미만 | 관리종목 지정 사유 해당 |

- 감사의견 API에는 감사범위 제한 전용 필드가 없다. 범위제한 여부를 판별할 수 없으면(`fin.audit_scope_limitation=unknown`) R1b-KS와 R1-KQ의 감사범위 제한 부분은 "확인 불가"로 표시한다. 입력 지표가 `unknown`(정정 전 원본 값 확인 불가)이어도 "확인 불가"다.

- 넣지 않은 규칙: 회생·워크아웃 기업 지원 제외(국민성장펀드 가이드북 원문 미확인), 시가총액·주가·매출액 요건, 2회 연속 감사의견 미달, 계속기업 불확실성 관련 요건. 회생·워크아웃 관련 공시는 사실(공시명·링크)로만 보여준다.
- 규칙 파일에 출처 문서명과 기준일을 함께 저장하고, 개정 시 원문 확인 후 갱신한다. 상세는 오케스트레이터 개발문서 v0.2 5장.

# 6. 신뢰성 원칙 (Architecture Guardrails)

1. **판단 분리**: 개별 에이전트는 판단하지 않는다 (1.2 참조). 금지 필드는 스키마 검증으로 막는다.
2. **LLM 계산 배제**: 모든 수치 연산은 `core.calc`의 Python 함수로만 한다. LLM은 텍스트에서 값을 찾아 근거와 함께 넘기기만 한다.
3. **근거 추적제**: 모든 수치·사실에 evidence_id를 붙이고, 없으면 저장을 거부한다. 형식: `DART:{rcept_no}:{section}`, `DART:{rcept_no}:{api}:{field}`, `FIN:{rcept_no}:{fs_div}:{account_id}`, `KRX:{basDd}:{isu_cd}:{field}`, `NEWS:{sha1(url)[:12]}`, `PUB:{기관}:{문서}`, `CALC:{run_id}:{metric_id}`.
4. **시점 누수 방지**: 공시는 접수일, 뉴스는 보도일, 재무제표는 해당 보고서 접수일 기준으로 as_of 이후 데이터를 수집 단계에서 차단한다. LLM 사전지식 유입은 '근거 없는 주장 금지 + 근거 날짜 ≤ as_of' 검증으로 막는다.
5. **지표 정의 단일 원천**: metrics_catalog.yaml에 등록된 지표 ID·산식만 쓴다. 미등록 지표는 출력하지 않는다.
6. **부분 실패 처리**: 한 에이전트가 실패하거나 외부 API(KRX 등)가 막히면 남은 결과로 검토서를 만들고, 상단에 '부분 검토서'와 누락 항목을 명시한다. 실패를 숨기지 않는다.
7. **LLM 호출**: 로컬 구독 CLI(`claude -p`)로 호출한다. 호출 횟수·소요 시간을 실행 로그에 남긴다.
8. **제한된 자율성**: LLM은 4.6의 판단 지점에서 허용된 선택지만 고른다. 모든 결정은 이유·근거와 함께 기록한다.
9. **사용자 조건과 시스템 판단의 구분**: 보드의 필터·정렬은 사용자가 정한 조건과 출처 있는 수치로만 한다. 시스템이 만든 점수나 순위로 정렬하지 않는다.

# 7. 최종 산출물

산출물은 두 가지다. **발굴 보드**가 대표 산출물이고, **사전검토서**는 보드에서 기업을 선택했을 때 보는 상세 문서다.

## 7.1 발굴 보드 (DiscoveryBoard)

탐색 조건 1건당 보드 1개를 만든다. 행은 `BoardRow`이고 모든 값은 출처 있는 사실이다.

| 열 | 내용 | 출처 |
|---|---|---|
| 기업 | 기업명, 시장, 업종 | DART 기업개황 |
| 해외 프로젝트 | 국가, 방식(신설·증설·M&A), 단계(Stage 1~5) | ovs |
| 해외 투자액 | 금액과 금액 출처 구분(공시·보도) | ovs.overseas_investment_amount |
| 자금 공백 | 금액, 자금 공백 비율 | ovs.funding_gap, ovs.funding_gap_ratio |
| 재무 핵심 | 부채비율 + 영업현금흐름(TTM), 각각 기준 기간(최신 정기보고서) 표시 (2026-11-05 변경) | fin (`fin.debt_ratio`, `fin.ttm_operating_cash_flow`) |
| 규칙 결과 | 5장 규칙(시장별) 해당 여부 배지 | apply_rules |
| 최근 신호일 | 마지막 관련 공시·보도 날짜 | ovs |
| 변경 배지 | 신규 매칭, 단계 변화, 금액 변경, 연기·철회 | monitor_graph |
| 검증 상태 | 검증 통과 / 검증 실패 항목 있음 / 부분 결과 | verifier |

- 기본 정렬은 최근 신호일이다. 사용자는 자금 공백 비율, 투자액 등 출처 있는 수치 열로 정렬을 바꿀 수 있다.
- '심층 분석 대기' 행과 '제외 목록'(제외 조건과 값)을 보드 하단에 함께 둔다. 시스템이 무엇을 빼고 왜 뺐는지 숨기지 않는다.
- 상단에는 단계별 기업 수(4.0)와 `summarize_board`의 사실 요약을 둔다.

## 8.1 화면 공통 원칙

- 화면은 SQLite를 읽기만 하고, 그래프 실행은 별도 worker 프로세스가 `orc_jobs`를 처리한다. 화면을 새로고침해도 실행이 끊기지 않는다.
- 화면에서 수치를 다시 계산하지 않는다. 표시 값은 모두 저장된 `AgentResult`·`DiscoveryBoard`·`FinalReport`에서 가져온다.
- 평가어·점수·순위 표시를 쓰지 않는다. 배지는 '관리종목 지정 사유'처럼 사실만 적는다.
- 진행 단계(1~5)는 표 위 범례로 이름을 함께 보여준다: 검토·언급 → 계획 발표 → MOU·협약 → 이사회 결의 → 착공·인수 완료.
- 신용평가 기준표 구간 막대·배경 띠는 MVP에 없다(Phase 2). 수치는 값·사업연도·산식 출처만 보여준다.
- 실행 로그(노드 경로, LLM 판단 D1~D4)는 화면에 두지 않고 `decisions` 테이블과 `python -m stride.cli show --run-id`로 확인한다. 본선 데모에서 필요하면 기업 상세의 '근거 목록' 탭 아래에 접힌 영역으로 추가한다.

## 10.1 성능 검증: 백테스트 (시점 리플레이)

운영 기능이 아니라 **일회성 성능 평가**다. 다만 심사 과정에서 다른 사례로 다시 돌려볼 수 있도록 `scripts/replay.py`로 작성한다. 시점 테스트(as_of 이후 근거 0건)와 같은 도구를 쓴다.

| 항목 | 내용 |
|---|---|
| 사례 선정 | 과거에 해외투자 목적의 자금 조달 공시(유상증자, 전환사채 등에서 자금 사용 목적이 해외 시설·지분 취득인 건)가 있었던 기업 |
| 실행 방법 | as_of를 조달 공시일의 3개월 전, 6개월 전으로 두고, 해당 기업이 포함될 만한 일반 조건으로 discover_graph 실행 |
| 측정 지표 | 사전 포착률(조달 공시 전 보드에 나타난 비율), 평균 선행 기간(첫 포착일 → 조달 공시일), 보드 정확도(보드에 오른 기업 중 해외투자 신호가 실제 공시로 확인되는 비율, 사람이 직접 확인), **정정공시 영향 건수**(as_of가 원공시일~정정일 사이라 값이 `unknown`이 된 공시·보고서 수, `runs.unknown_count`) |
| 한계 명시 | 사례 수가 적어 일반화하지 않는다. 조달 공시가 없었던 기업은 '틀림'이 아니라 '조달 방식 미확인'으로 분류한다. LLM이 학습한 사후 지식이 섞일 수 있으므로, 근거 날짜 ≤ as_of 검증을 통과한 주장만 집계한다 |
| 산출물 | 사례별 표(기업, 첫 포착일, 조달 공시일, 선행 기간, 근거, 정정공시 영향 건수)와 요약 수치. 기획서·발표 자료에 사용 |
